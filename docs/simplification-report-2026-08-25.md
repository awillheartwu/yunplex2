## 结论

本轮不是一次局部 UI 清理，而是完成了产品入口、匹配模型、运行记录、日志和数据生命周期五个方向的收敛。以所选基线计算，受版本控制的代码与样式行数从 60,152 行降至 46,038 行，减少 14,114 行（23.5%）；Git 净变化为 -14,368 行。

现在的产品主路径可以概括为：

1. 在同步源中定义网易云目标。
2. 通过唯一的 Source Convergence 链路下载、绑定并收敛 Plex 歌单。
3. 任务中心只展示进行中任务和可处理异常。
4. 系统与运行统一承载监控、诊断日志和历史运行记录。

原先围绕“动态、匹配管理、下载历史、任务历史、日志、系统维护”形成的多套入口和重复投影已基本消失。复杂度没有被简单转移到 UI 后面：MusicBrainz/provider 候选匹配、活动事件、完整单曲运行快照和常规成功日志也从后端与数据库中退役。

## 已经砍掉或合并的产品表面

### 运维入口

- 删除“动态”页面、活动时间线、活动事件 API 和 `activity_events` 持久化链路。
- 将系统监控、系统日志、运行记录合并为 `/system` 下的三个 tab。
- `/task-center` 收敛为实时任务和可行动异常；完整历史统一进入系统页。
- 删除 `/jobs`、`/logs`、`/sources` 等旧兼容页面，不再长期维护重定向壳。
- 仪表盘删除最近活动、最近 Plex、重复 KPI 和配置展示，只保留当前任务、来源健康和异常摘要。

### 下载

- 删除独立下载历史页、下载日统计和图表，以及批量清理、整表删除、重复重试等冗余 API。
- 手动下载页只负责创建一次性任务；任务中心负责实时状态和失败操作；系统页负责历史查询。
- 下载队列、单曲下载、标签写入、Local Media Asset 登记等同步主链路依赖仍完整保留。

### 媒体复用与匹配

- 自动复用规则缩减为“托管文件的 Plex 精确路径一致”。
- 外部媒体必须由用户明确接管；不能确认时自动下载带网易云歌曲 ID 的独立副本。
- 删除 MusicBrainz/provider 身份、弱元数据候选、艺人候选解析、审核队列和批量决策链路。
- 日常媒体复用进入同步源歌曲详情；全局匹配页降级为只处理孤立关联的高级入口。
- 保留 `song_identity_bindings`、`local_media_assets`、绑定版本、原子替换、Plex 写后读回和按 `playlistItemID` 删除等安全边界。

### 状态与失败

- `failure_records` 成为异常事实源，来源健康、任务中心和重试都从同一读模型派生。
- 删除来源 JSON 内的失败缓存、独立 match-review 状态和重复刷新目标接口。
- 同一来源的一次运行只在收敛提交点投影异常，降低状态分叉和排查路径。

## 数据库与日志收敛

历史测试数据库的实际体积变化为：

`137 MB → 27 MB → 约 11.2 MB → 2.2 MB`

当前 `data/data.db` 为 2,326,528 字节，较 137 MB 备份约减少 98.4%；`integrity_check=ok`，无 freelist 残留。当前关键记录量：

- `task_runs`：311 条摘要。
- `task_run_song_changes`：208 条有变化或异常的单曲记录。
- `logs`：0 条（历史常规日志已清理，后续按需重新积累诊断记录）。

运行记录已从“每次反复覆盖完整 songs JSON”改为：

- `task_runs` 保存可检索摘要、计数、步骤和状态。
- `task_run_song_changes` 只保存新增媒体、错误、版权/忽略、路径或 Plex 操作等有意义变化。
- 无变化的 `skipped_existing` 只进入聚合计数，不再逐曲持久化。
- 完整详情最多保留 7 天，并受 8 MiB 总预算限制；成功运行保留 7 天，失败/部分成功保留 14 天。

日志系统也从“业务流水账”改为“诊断证据”：

- 常规成功、跳过和每曲进度不写持久日志。
- 只保留警告、错误、启动/维护等真正需要排障的信息。
- 日志最多保留 30 天且不超过 2,000 条，由统一生命周期维护自动清理。
- 删除手工清空日志 API，避免 UI 中出现高风险、低价值的维护操作。

## 被刻意保留的复杂度

以下部分没有为了行数而删减，因为它们承担数据安全责任：

- Source Convergence 仍是同步、下载、身份绑定和 Plex mutation 的单一编排入口。
- 网易云目标 occurrence 与 Plex `playlistItemID` 分离，删除只作用于具体歌单项，不删除媒体文件。
- 绑定版本检查、精确路径验证、原子替换、Plex 写后读回和冲突中止仍保留。
- Local Media Asset 与 Media Link 仍是跨刮削器稳定复用的事实基础。
- 失败摘要、可操作异常、重试所需上下文和历史运行检索仍保留。

这意味着当前精简的目标是“减少重复模型和重复入口”，不是把安全收敛降级为不可审计的复制脚本。

## 仍然存在的主要复杂度

1. `server/lib/db/migrations.ts` 仍约 799 行。现在不需要旧版本兼容，但历史迁移尚未重置为新的 schema 基线，这是下一次代码体积精简最明确的对象。
2. `server/lib/sync/service.ts` 仍约 636 行。虽然已经拆出下载、Plex reconciliation、纯重排和 finalization，但主编排仍需要持续守住单一路径边界。
3. 来源修复接口仍有独立操作路径，需要继续确认它是否可以完全收敛到 Source Convergence 命令模型。
4. 自动调度仍是全局定时扫描，不是来源级持久队列；这是可靠性欠账，不应与本轮“删功能”混淆。
5. 当前验证是本地测试、lint、typecheck、仓库大小门禁和生产构建；尚未完成真实网易云、Plex、多 scraper、重启和长时间运行 E2E。

## 阶段判断

按产品表面看，本轮计划中的 S0–S6 已经完成，可以认为“第一轮大规模精简”关闭：一级入口减少四分之一，页面减少三分之一，API 减少约五分之一，代码与样式减少接近四分之一，历史测试库体积减少约 98%。

按维护成本看，项目已经从“多个页面解释多个状态模型”转为“少数工作区消费统一事实源”。下一阶段不宜继续横向砍入口，而应优先做两件事：建立新的 SQLite schema 基线，以及把自动同步升级为可恢复的来源级持久任务队列。前者继续降低代码和迁移心智，后者解决当前最主要的无人值守可靠性风险。
